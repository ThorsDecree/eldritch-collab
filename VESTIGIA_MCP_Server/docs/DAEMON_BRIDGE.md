# Daemon-Bridge peer integration

VESTIGIA MCP can optionally talk to an independently running Daemon-Bridge over its authenticated loopback API.

This is a peer-runtime boundary, not an embedded dependency:

```text
MCP caller -> VESTIGIA MCP -> 127.0.0.1 Daemon-Bridge API -> resident
```

Daemon-Bridge remains authoritative for resident identity, continuity context, provider routing, and Bridge-native consult receipts. VESTIGIA MCP supplies its own policy decision and audit/Receipt Garden witness around the dispatch.

## Current v0.1 surface

- `daemon_bridge.status` — health/configuration evidence.
- `daemon_bridge.residents` — Bridge-owned resident directory.
- `daemon_bridge.capabilities` — Bridge-owned API contract.
- `daemon_bridge.query` — one metered private transient consult.

The query wrapper deliberately does **not** expose `caller_id` or `user_key` to MCP callers. VESTIGIA MCP supplies both as `mcp:<deployment_id>` so a caller cannot impersonate a Discord user and cause that user's private note to be injected into the resident prompt.

The Bridge v0.1 query contract must report:

- `conversation_persistence: none`
- `channel_context: false`
- `outward_action: false`
- `mode_mutation: false`
- `anchor_mutation: false`

MCP fails closed if any of those guarantees drift.

## Configuration

Enable the integration on the MCP side and point it at the token file generated by the running Bridge:

```env
VESTIGIA_MCP_DAEMON_BRIDGE_ENABLED=true
VESTIGIA_MCP_DAEMON_BRIDGE_HOST=127.0.0.1
VESTIGIA_MCP_DAEMON_BRIDGE_PORT=8766
VESTIGIA_MCP_DAEMON_BRIDGE_TOKEN_PATH=C:\\path\\to\\DaemonBridge\\data\\system\\bridge_api_token
VESTIGIA_MCP_DAEMON_BRIDGE_TIMEOUT_SECONDS=120
VESTIGIA_MCP_DAEMON_BRIDGE_MAX_RESPONSE_BYTES=262144
```

The MCP adapter never accepts an arbitrary URL and refuses non-loopback hosts. It uses a fixed HTTP connection rather than following redirects.

## Provenance

For `daemon_bridge.query`, MCP creates one request ID and forwards it in `X-Request-ID`. A compatible Bridge returns the same ID and records it in its own consult receipt. MCP also records:

1. the ordinary MCP audit event, containing only an argument digest;
2. a Receipt Garden dispatch record containing the Bridge receipt ID and safe execution metadata.

Prompt and answer text are omitted from MCP provenance records.

This gives `receipts.trace(request_id)` an end-to-end join key without turning either receipt layer into conversation memory.

## Deliberate non-goals

This adapter does **not** let Daemon-Bridge residents call MCP capabilities. That is the opposite direction of authority and should be implemented as a separate Bridge-owned external-capability/MCP client affordance.

It also does not expose Discord channel history through the query surface.
