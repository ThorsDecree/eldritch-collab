# GIF Forge Implementation Plan

> Execute inline with test-driven-development; obtain a fresh whole-branch review before PR publication.

**Goal:** Add native GIF rendering and a resident-owned motion planning, revision, and inspection workflow.

**Architecture:** A typed render specification follows the existing image service and durable queue. Byte-derived media metadata lives additively in asset source JSON. Immutable Forge recipes refer to existing shelf IDs and render through the same queue; previews are private derived shelf assets.

**Tech Stack:** Python 3.11+, SQLite, Pillow, existing OpenAI SDK adapter; pytest with simulated providers.

**Spec:** Approved GIF rendering and GIF Forge checkpoint, summarized in the constraints and tasks below.

## Global constraints

- Existing still-image defaults, private generation, review, and explicit sharing remain intact.
- `background` continues to mean asynchronous execution.
- Expose output_format, frame_count, frame_duration_ms, size, quality, complexity. GIF limits: 2-16 frames, 20-2000 ms rounded to 10 ms. Model route is operator-owned.
- No credentials copied or changed; no live API calls; no changes to the running deployment. Jeff performs live verification.
- Preserve original bytes. Requested settings and actual measured output are distinct.
- A stale running render must not silently be billed again. No recurring generation bells.

## Review focus

1. Nonuniform timing, absent loop extension, and coalesced frames must report measured values, not requested values (task 1/2).
2. Config changes between enqueue and execution must not change the stored recipe (task 2).
3. Mislabeled, malformed, static, or oversized results must fail before saving partial output (task 2).
4. Other-resident IDs and unknown fields must fail without rendering or revealing source contents (task 3).
5. Revision branches, inspection derivatives, and completion receipts must preserve parentage and private sharing (task 3/4).
