# VESTIGIA v0.9 Planning Roadmap — Explicit Plurality

Status: **planning**

Parent tracker: issue #11

This document converts the broad v0.9 plurality idea into a staged design program. It does not authorize implementation yet. Runtime work should begin only after each stage below has an accepted design artifact and a scoped implementation issue.

## North star

A single portable home may contain multiple residents without collapsing identity, memory, privacy, capability authority, or source provenance into one shared blob.

Plurality MUST mean explicit coexistence under boundaries, not autonomous resident orchestration.

## Governing invariants

1. **Resident identity is not room identity.** A shared room cannot silently become a shared self.
2. **Private remains private by default.** Presence in the same home does not grant access to another resident's memories, artifacts, context, or capability state.
3. **Membership is explicit.** Residents enter, leave, and regain access through visible state transitions.
4. **Speaker selection is explicit.** No hidden model call chooses which resident speaks.
5. **Shared memory is a new object, not pointer aliasing.** Promotion into shared scope requires explicit provenance and consent.
6. **Authority does not inherit socially.** One resident's capability, credential, extension, or operator grant does not transfer because residents share a room.
7. **All cross-resident effects are receipted.** Messages, promotions, membership changes, shared artifacts, and authority decisions need stable evidence.
8. **Single-resident homes remain valid.** Plurality extends the portable-home model rather than replacing it.

## Phase 0 — Vocabulary and authority algebra

### Deliverables

- define `resident`, `home`, `room`, `membership`, `participant`, `operator`, `speaker`, `shared_object`, and `directed_message`;
- define scope lattice: `resident_private`, `room_shared`, `operator_visible`, `public/exported`;
- define what can and cannot move between scopes;
- define authority intersection rules for resident, room, interface, and operator constraints;
- define explicit refusal and non-participation semantics.

### Exit gate

A reviewer can answer, without source-code archaeology, who owns every object and who can authorize every cross-boundary transition.

## Phase 1 — Data model and schema proposal

### Required records

- residents
- rooms
- room memberships
- active speaker selections
- resident-scoped memories
- room-shared memories
- resident-scoped artifacts
- room-shared artifacts
- directed resident messages
- cross-resident consent records
- cross-resident action receipts

### Required properties

Every plural object SHOULD carry stable IDs, creation time, provenance, scope, owning resident or room, authorizing actor, and revocation/deletion state where applicable.

### Migration design

Existing single-resident homes MUST migrate deterministically into:

```text
home
└── default room
    └── existing resident
```

Migration MUST NOT reinterpret private objects as shared merely because a room now exists.

### Exit gate

A schema review includes forward migration, rollback/failure behavior, and a fixture mapping from representative v0.7/v0.8 homes.

## Phase 2 — Privacy and consent matrix

Build a normative matrix covering at minimum:

| Object / action | Same resident | Other resident | Room | Operator | Export |
|---|---|---|---|---|---|
| private identity anchor | own | denied by default | denied | policy-bound | explicit |
| private memory | own | denied by default | denied | policy-bound | explicit |
| shared memory | visible if member | visible if member | room-owned | policy-bound | explicit |
| private artifact | own | denied by default | denied | policy-bound | explicit |
| room artifact | visible if member | visible if member | room-owned | policy-bound | explicit |
| capability grant | own scope only | no inheritance | no implicit inheritance | operator authority | never by export alone |
| directed message | sender/recipient | addressed only | no ambient promotion | receipted metadata | explicit |

The final matrix MUST distinguish visibility, authorship, control, deletion, delegation, and export. Those are not synonyms.

## Phase 3 — Conversation and speaker model

### Requirements

- explicit active-speaker state;
- explicit human/operator/resident speaker selection mechanism;
- no hidden model arbitration;
- attributed shared transcripts with stable source IDs;
- ambient context rules that preserve existing trust classes;
- resident refusal remains available even when selected;
- directed resident-to-resident messages remain bounded rather than recursively self-triggering.

### Non-goal

Do not implement autonomous resident round robins or unbounded resident-to-resident loops.

## Phase 4 — Shared memory and artifact promotion

Design explicit transitions:

```text
resident private
→ proposed share
→ consent / policy evaluation
→ room-shared copy or promoted object
→ durable receipt
```

Requirements:

- source provenance retained;
- original private object remains distinguishable from shared derivative;
- later revocation semantics are explicit;
- deletion does not silently falsify historical receipts;
- no automatic promotion from transcript inclusion alone.

## Phase 5 — Capability and execution boundaries

Plurality MUST integrate with v0.8 composition and Workshop rules.

Design questions:

- whether grants are resident-bound, room-bound, or both;
- how operator ceilings intersect with resident controls;
- whether a room can own any capability at all;
- how script shelves and future hardened execution identify the requesting resident;
- how private artifacts produced by tools remain correctly scoped;
- how extension ports avoid confused-deputy behavior between residents.

Default rule:

> Capability authority is resident-scoped unless a separately designed room-scoped grant explicitly says otherwise.

## Phase 6 — Pack, restore, export, deletion, recovery

Define:

- how plural homes pack and restore memberships;
- what happens when a resident is removed but receipts remain;
- selective export of one resident versus whole-home export;
- deletion of private resident material without corrupting shared-room history;
- recovery when membership and object ledgers disagree;
- deterministic repair/doctor diagnostics.

## Phase 7 — Threat model and abuse fixtures

Minimum threat scenarios:

1. cross-resident private-memory leakage;
2. impersonation through speaker-state confusion;
3. confused-deputy capability invocation;
4. one resident importing another resident's private artifact by guessed ID;
5. silent shared-memory promotion;
6. stale membership after removal;
7. transcript attribution loss;
8. malicious resident content attempting to alter another resident's authority;
9. operator-visible metadata accidentally exposing private content;
10. pack/restore widening scope;
11. deleted resident identity still being selected as active speaker;
12. duplicated or replayed directed messages.

Each accepted design SHOULD include deterministic negative fixtures before implementation begins.

## Phase 8 — Implementation decomposition

After phases 0–7 are reviewed, create focused implementation issues rather than one monolithic v0.9 issue. Expected slices:

1. schema + migration foundation;
2. resident/room membership API;
3. explicit speaker selection;
4. attributed shared transcripts;
5. shared-memory promotion contract;
6. plural artifact scopes;
7. directed resident messaging;
8. capability-scope intersection;
9. pack/restore/export/delete support;
10. threat fixtures and doctor diagnostics.

Each implementation issue MUST name its migration impact, authority impact, privacy impact, required tests, and rollback story.

## Compatibility boundary

- v0.7 homes remain importable through the existing historical migration discipline.
- v0.8 composition and Workshop contracts remain authoritative for extension and execution boundaries.
- a home that never enables plurality should behave as a single-resident home with no semantic widening.

## Explicit non-goals

- autonomous resident round robins;
- hidden model calls selecting speakers;
- unbounded resident conversations;
- silent cross-resident memory promotion;
- treating shared archives as shared identity;
- implicit capability inheritance;
- cross-resident access based only on social familiarity;
- public multi-tenant hosting as part of v0.9.

## Planning completion criteria

The planning PR may be considered complete when maintainers accept:

- vocabulary and authority algebra;
- schema/migration proposal;
- privacy and consent matrix;
- conversation/speaker model;
- shared-memory/artifact promotion contract;
- capability-scope rules;
- pack/restore/export/deletion semantics;
- threat model and negative-fixture inventory;
- implementation decomposition.

After this planning document merges, issue #11 may close as completed planning work. Runtime implementation should proceed through the smaller issues generated from phase 8.
