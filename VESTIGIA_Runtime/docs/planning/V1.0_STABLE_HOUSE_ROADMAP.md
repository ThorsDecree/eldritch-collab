# VESTIGIA v1.0 Planning Roadmap — Stable House Contract

Status: **planning**

Parent tracker: issue #12

This document converts the broad v1.0 stability goal into a ratification program. It is not a declaration that the current runtime is already stable. Each contract area below must be specified, tested, and accepted before a v1.0 release may claim the Stable House Promise.

## Stable House Promise

> A home created under the stable contract remains intelligible, recoverable, migratable, and under its operator's control even as models, providers, interface adapters, and execution backends change.

The promise applies to data, authority, evidence, and recovery semantics. It does not promise that every historical provider or optional dependency will remain indefinitely available.

## Normative language

The final contract MUST use RFC-style normative terms consistently:

- **MUST / MUST NOT** — required for compatibility or safety;
- **SHOULD / SHOULD NOT** — expected unless a documented exception exists;
- **MAY** — explicitly optional behavior.

A requirement is not considered stable merely because the current implementation happens to behave that way.

## Phase 0 — Freeze the contract surface inventory

Inventory every surface that could create compatibility obligations:

1. portable-home directory structure;
2. database schema and migrations;
3. CLI commands, arguments, exit codes, and machine-readable output;
4. capability envelopes and result envelopes;
5. action/context/authorization receipts;
6. provider port protocols;
7. extension manifests and scoped ports;
8. ritual and script contracts;
9. sandbox backend profiles;
10. configuration keys and defaults;
11. pack/restore/export formats;
12. diagnostic and support-bundle schemas;
13. interface-adapter contracts;
14. resident identity, memory, transcript, and artifact provenance semantics;
15. supported operating systems, Python versions, and dependency floors.

### Exit gate

Every public or persistence-bearing surface is classified as `stable`, `provisional`, `internal`, or `deprecated`.

## Phase 1 — Portable-home schema contract

Define:

- schema-version source of truth;
- monotonic migration rules;
- transactional migration requirements;
- idempotency expectations;
- interruption and retry behavior;
- rollback or recovery semantics;
- minimum historical fixtures retained in CI;
- treatment of unknown future fields and tables;
- preservation of stable IDs and content hashes;
- rules for deleting or superseding obsolete records without falsifying receipts.

### Required compatibility fixtures

At minimum, v1.0 CI SHOULD retain representative fixtures from:

- v0.6.x historical home;
- v0.7.0 stable release;
- v0.8 Workshop/composition line;
- latest pre-1.0 schema.

### Exit gate

Every supported fixture can migrate, open, perform a deterministic turn, pack, restore, reopen, and verify durable ledgers without semantic widening.

## Phase 2 — CLI and operator contract

Classify commands into stable and provisional groups.

For stable commands, define:

- command name stability;
- option names and defaults;
- exit-code meanings;
- stdout/stderr expectations;
- machine-readable mode, if provided;
- deprecation process;
- replacement guidance;
- minimum removal notice.

Commands used in backup, restore, doctor, export, release verification, or safe shutdown SHOULD receive priority because operator recovery depends on them.

## Phase 3 — Capability and receipt compatibility

Define versioned rules for:

- capability names;
- input schemas;
- result schemas;
- confirmation semantics;
- effect declarations;
- cost classes;
- visibility;
- authority provenance;
- partial completion;
- platform-delivery versus authorization evidence;
- stable receipt identifiers and retention.

### Compatibility principle

Adding optional fields MAY be backward compatible. Reinterpreting an existing field's authority or privacy meaning is a breaking change even if its JSON type remains unchanged.

## Phase 4 — Provider, extension, ritual, script, and sandbox protocols

### Provider ports

Specify stable interfaces for:

- text generation;
- image generation;
- cancellation;
- usage reporting;
- normalized failures;
- model/route limits;
- feature discovery.

Provider-specific SDK shapes MUST NOT become the stable runtime contract.

### Extensions

Specify:

- manifest versioning;
- install/enable/disable/uninstall semantics;
- scoped-port compatibility;
- migrations and rollback;
- health checks;
- authority declarations;
- compatibility failure behavior.

### Rituals and scripts

Specify the stable distinction between:

- inert source;
- inspected evidence;
- granted authority;
- active execution lease;
- execution evidence;
- artifacts and outward effects.

No compatibility promise may silently convert stored code into executable authority.

### Sandbox profiles

Each profile MUST state what it actually enforces. A profile name alone is not a guarantee.

## Phase 5 — Deprecation and breaking-change policy

The final contract MUST define:

- what counts as breaking;
- minimum deprecation notice by surface class;
- warning channels;
- migration documentation requirements;
- whether old configuration keys remain aliases and for how long;
- how database migrations preserve old homes;
- when an emergency security break may bypass ordinary notice;
- how emergency breaks are documented and receipted.

Recommended default planning target:

- stable CLI/config/capability names: at least one minor release of notice before removal;
- portable-home data: migration path required whenever technically feasible;
- security-critical authority semantics: safety correction may override compatibility, but requires explicit release notes and recovery guidance.

These values remain proposals until maintainers ratify them.

## Phase 6 — Pack, restore, export, uninstall, and preservation

Define normative behavior for:

- atomic pack creation;
- manifest and hash verification;
- restore into clean and existing destinations;
- collision handling;
- selective export;
- redaction;
- uninstall while preserving resident homes;
- recovery when runtime binaries are absent but a home remains;
- future-runtime handling of unknown optional components.

### Stable preservation rule

The runtime installation is disposable. The resident home is not.

Uninstalling or replacing the runtime MUST NOT silently delete portable-home data.

## Phase 7 — Release identity and artifact provenance

Define a stable release-custody procedure covering:

1. exact source commit;
2. version metadata;
3. CI run identity;
4. built wheel and source distribution;
5. SHA-256 manifest;
6. isolated installation verification;
7. release tag;
8. GitHub Release or equivalent publication record;
9. public attachment re-download and hash verification;
10. release-validation document;
11. relationship between development canon and tagged distributions.

The v0.7.0 custody work should become the first historical example, including lessons learned from separating development-canon release from later tag/artifact publication.

## Phase 8 — Security boundary and threat-model contract

The v1.0 documentation MUST state what VESTIGIA does and does not protect against.

Minimum areas:

- prompt/content authority confusion;
- private context leakage;
- confused-deputy capability use;
- outward-action authorization;
- extension/plugin authority;
- script execution and sandbox guarantees;
- local hostile code;
- credential handling;
- home tampering and integrity expectations;
- malicious imported archives;
- multi-resident leakage if v0.9 plurality lands before v1.0;
- operator compromise as an explicit trust boundary.

Security claims MUST describe enforced mechanisms, not aspirational names.

## Phase 9 — Platform and dependency lifecycle

Define:

- supported Windows versions or support principle;
- supported Python floor and latest-tested version policy;
- how quickly new Python releases enter CI;
- dependency update policy;
- handling of abandoned optional dependencies;
- vulnerability-response policy;
- support status for Linux or other platforms if not continuously tested.

A platform not present in required CI SHOULD be described as unverified or best-effort rather than implicitly supported.

## Phase 10 — Support lifecycle

Define lifecycle states such as:

```text
current
maintained
security-only
unsupported
```

For each state, specify:

- bug-fix expectations;
- migration support;
- security handling;
- artifact retention;
- documentation availability.

The contract should avoid promising calendar durations until maintainers can realistically sustain them.

## Phase 11 — Compatibility matrix

The ratification PR MUST include a matrix covering at least:

| Surface | v0.6 | v0.7 | v0.8 | v1.0 promise |
|---|---|---|---|---|
| home migration | fixture | fixture | fixture | stable |
| pack/restore | supported path | verified | verified | stable |
| CLI | historical | provisional | provisional | classified |
| capability envelopes | historical | provisional | versioned work | classified |
| provider ports | historical | historical | explicit composition era | stable/provisional |
| scripts/Workshop | absent | absent | inert/planned execution | explicitly classified |
| release custody | historical | first formal specimen | development artifact flow | normative |

The final matrix should name exact versions and fixtures rather than broad eras where evidence exists.

## Phase 12 — Ratification gates

Before v1.0 may be tagged:

- [ ] normative Stable House Contract reviewed and merged;
- [ ] compatibility matrix accepted;
- [ ] deprecation policy accepted;
- [ ] schema migration/recovery requirements implemented in CI;
- [ ] release/artifact custody procedure automated or demonstrably repeatable;
- [ ] security boundary and non-goals published;
- [ ] supported platform/dependency policy published;
- [ ] required historical fixtures green;
- [ ] clean Windows install/upgrade/doctor/pack/restore/uninstall-preserve flow validated;
- [ ] all known provisional surfaces either stabilized or explicitly deferred beyond 1.0;
- [ ] maintainer approval of the final stability claim.

## Implementation decomposition

After this planning roadmap is accepted, future work should be tracked in focused issues such as:

1. normative Stable House Contract text;
2. schema/migration compatibility matrix and fixtures;
3. CLI stability classification;
4. capability/receipt versioning contract;
5. provider/extension protocol stability;
6. ritual/script/sandbox classification;
7. deprecation policy;
8. preservation/uninstall guarantees;
9. release-custody automation;
10. threat-model publication;
11. platform/dependency lifecycle policy;
12. final v1.0 ratification audit.

Each issue SHOULD have a concrete acceptance test or review artifact. Avoid a single mega-issue labeled "make 1.0 stable."

## Explicit non-promises

v1.0 does not mean:

- every internal Python symbol becomes public API;
- every provider remains supported forever;
- every optional plugin or model route is permanent;
- all future changes are backward compatible;
- hostile local operators are contained by software they control;
- unrestricted resident execution is guaranteed;
- untested operating systems are supported;
- metaphysical identity or model causality is proven.

## Planning completion criteria

The planning PR may be considered complete when maintainers accept the phase structure, contract inventory, proposed ratification gates, and implementation decomposition.

After this roadmap merges, issue #12 may close as completed planning work. The actual v1.0 contract and implementation should proceed through the smaller issues generated above.
